uv instead of pip + venv by hand

  • uv sync installs from pyproject.toml / uv.lock.
  • uv run python … runs without activating the venv.
  • Dev tools: uv sync --group dev (includes langgraph-cli[inmem] + Windows colorama).

Who picks the Ollama model?

ollama serve exposes an HTTP API of already pulled models. It does not choose for you. Your code sends model: "…" on each request (ChatOllama(model=OLLAMA_MODEL)). Missing name → 404.

GPU: Ollama auto-uses the GPU when available (ollama ps shows PROCESSOR); Python does not enable CUDA itself.

Studio vs LangSmith

Studio is the LangSmith-hosted UI for LangGraph. Optional LANGSMITH_API_KEY in .env enables cloud traces; without it, local chat still works — you just will not see LangSmith runs.

LangGraph nodes are custom

No fixed official node names. You define functions and wire edges. Ours:

flowchart LR START --> ingest ingest --> prepare prepare --> generate generate -->|tool_calls| tools tools --> generate generate -->|done| END

flowchart — tutor pipeline + ReAct tool loop

NodeRole
ingestHarvest personal facts from the latest human text (regex)
prepareRebuild SystemMessage + soft compression
generateHard trim + model invoke (append one AIMessage)
toolsHITL interrupt() then ToolNode([get_time]) (or rejected ToolMessage)

After generate, tools_condition routes to tools or END. Inside tools, interrupt() pauses until the human resumes (Command(resume=…)). Needs a checkpointer. ingest/prepare could be merged; split for Studio clarity.

Common graph patterns (habits, not required APIs)

  • Pipeline — fixed steps (this repo).
  • ReAct — llm ↔ tools loop.
  • Router — classify then branch.
  • HITL — Human-In-The-Loop: pause for approval (interrupt).
  • create_agent — higher-level ReAct wrapper; compared in compare_create_agent.py (tutor graph stays custom).

create_agent vs graph_core

Default for real products: create_agent (model + tools ReAct, optional middleware / checkpointer). HITL interrupt + resume

Before running tools, the graph pauses with a JSON payload (action, tool_calls). Resume value becomes the return of interrupt().

sequenceDiagram participant U as Human participant G as Graph participant T as ToolNode G->>G: generate AIMessage with tool_calls G->>U: interrupt approve_tool_calls alt approve U->>G: Command resume true G->>T: run get_time T-->>G: ToolMessage G->>G: generate final reply else reject U->>G: Command resume false G->>G: ToolMessage rejected G->>G: generate again end

sequenceDiagram — tool approval HITL

  • CLI: graph_chatbot.py prompts y/N; type history to list checkpoint_id.
  • Studio: Interrupts panel → resume with boolean / JSON.
  • Time travel: pass checkpoint_id in configurable to continue from an older snapshot (same thread_id).
  • On resume the node restarts from the top — keep side effects after interrupt().

Checkpointing

  • Within one run: a snapshot after each step (Studio timeline).
  • Next turn: resume from that thread’s latest state.
  • You can target an older snapshot with checkpoint_id (time travel).
  • CLI: SqliteSaver → sessions/langgraph.sqlite.
  • Studio / langgraph.dev: platform persistence — must not compile the exported graph with a custom checkpointer.

Big picture

The app is one LCEL chain:

flowchart LR Topic[user topic dict] --> Prompt[prompt] Prompt --> Model[model] Model --> Parser[parser] Parser --> Out[string on screen]

flowchart — LCEL mental model

  • Prompt: turn a dict like {"topic": "LCEL"} into chat messages.
  • Model: send those messages to a local LLM (Ollama).
  • Parser: turn the model reply into a plain str.

LCEL composes steps with |:

chain = prompt | model | parser

Each piece is a Runnable. invoke runs them in order. Input is a dict because the prompt has named variables.

Prompt: ChatPromptTemplate

APIWhat it is
from_template("...{topic}...")One human message. Fine for a first demo.
from_messages([...])List of roles. This project uses this.
  • system: standing instructions (tutor; do not mix up names).
  • human: user request; {topic} filled at invoke time.

"{topic}" is not an f-string. LangChain substitutes on chain.invoke({"topic": topic}).

Model: ChatOllama vs Ollama

PieceWhat it is
OllamaNative app / service. HTTP default localhost:11434. Holds pulled models.
ChatOllamaPython client in .venv (via uv sync).

If Ollama is down, the Python chain fails even after a successful uv sync. temperature=0 is more deterministic, not “always correct”.

Port already in use on ollama serve usually means Ollama is already running (tray app) — that is fine.

Parser: StrOutputParser

Chat models return a message object. The parser pulls .content as a str. Without it you print something like AIMessage(...).

Running the chain

result = chain.invoke({'topic': topic})
  • invoke: wait for the full answer (first_chain.py, summarizer, chatbot replies so tool_calls stay visible).
  • stream: yield chunks (not used for chatbot replies; string stream would hide tool calls).
  • batch: several inputs at once (not used yet).

In first_chain.py, the while True loop is ordinary Python — not LangChain memory. Each invoke is independent. chatbot.py is the version that passes history.

Hallucination

An early run explained LangChain as a blockchain framework. The pipeline was fine; the model guessed from “Chain”.

  • A working chain ≠ a true answer.
  • Small local models hallucinate more with short prompts.
  • A system message that names the confusion is a cheap mitigation, not a guarantee.

Structured output (extract_paragraph.py)

Structured output gives typed fields instead of one string:

FieldTypeRule
summarystrA few sentences covering the paste.
paragraph_countintHow many paragraphs the model thinks exist.
authorstr | NoneOnly if stated; else null. Do not invent.
published_atstr | NoneYYYY-MM-DD only if stated.
 
structured_model = model.with_structured_output(
  ParagraphExtract,
  method='json_schema',
  include_raw=True,
)
chain = prompt | structured_model

include_raw=True: bad parse → dict with error instead of crashing. Python count_paragraphs is printed beside the model’s count for comparison. Chatbot facts still use regex for now.

Chatbot memory (chatbot.py)

Short-term memory is a list of messages:

[system, human, ai, human, ai, ...]

Each turn: append HumanMessage, invoke bound model, maybe ToolMessage, append final AIMessage.

MessagesPlaceholder('messages') injects the list. Reply chain: prompt | tool_model (no string parser). Long-term file memory: sessions/<id>.json. That is ordinary JSON, not a LangGraph checkpointer.

One tool (get_time)

Not create_agent. Two implementations:

  • chatbot.py — hand-written run_turn (at most one tool round in a Python loop).
  • graph_core.py — generate ↔ tools via tools_condition + ToolNode (graph can loop until the model stops calling tools; recursion limit is the safety valve).
flowchart TD Inv1[invoke model] --> Check{tool_calls?} Check -->|yes| Run[run get_time] Run --> TM[append ToolMessage] TM --> Inv2[invoke again] Inv2 --> Print[print final text] Check -->|no| Print

flowchart — chatbot.py one-round tool loop

chatbot.py run_turn:
  invoke
  -> if AIMessage.tool_calls: run get_time, append ToolMessage, invoke again
  -> print the final text

graph_core:
  generate --tools_condition--> tools
  tools: interrupt() then ToolNode (or reject)
  tools --> generate
  generate --no tool_calls--> END

ToolMessage.tool_call_id must match the requesting AI tool call. Hard trim uses start_on='human' so a cut never starts on a dangling tool message.

Compression: soft summary, then hard trim_messages

flowchart TD Full[full messages] --> Soft{too many msgs or tokens?} Soft -->|yes| Sum[soft summarize older turns] Sum --> Pin[facts stay on SystemMessage] Soft -->|no| Hard Pin --> Hard[hard trim_messages by tokens] Hard --> Model[model]

flowchart — soft then hard compression

full messages
  -> if too many messages OR tokens: soft-summarize older turns
     (facts stay in a Python dict on SystemMessage)
  -> trim_messages by approximate tokens (hard backup)
  -> model

Soft: fold old turns into topic notes; pin personal facts in Python so a bad summarizer cannot wipe names.

Hard: token budget MAX_CONTEXT_TOKENS = 2048, strategy='last', include_system=True, start_on='human'.

trim_messages(
  messages,
  max_tokens=MAX_CONTEXT_TOKENS,
  token_counter='approximate',
  strategy='last',
  include_system=True,
  start_on='human',
)
